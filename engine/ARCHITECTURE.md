# Metacode Engine Architecture

The engine reads YAML specs and writes a working app. This document is the map:
what runs in what order, who owns which generated file, and where a new spec
kind or a new language goes.

For *why* a rule exists, see [docs/decisions.md](../docs/decisions.md).

## The pipeline

```
metacode run
  1  discover      find the metacode/ folder above the working directory
  2  parse         read project.yaml, data.yaml, ui.yaml, behaviors.yaml
  3  build         raw YAML -> model, by asking each spec kind's rules
  4  resolve       cross-reference symbols, resolve widget-event -> store-action
  5  scaffold      write the project, the stores, the dumb widgets
  6  plan          decide what to generate: one wrapper per page, one test per scenario
  7  wrappers      write the layer that wires widgets to stores
  8  tests         write one test per scenario
  9  prune         delete generated files whose spec source is gone
 10  implement     one LLM request writes the behavior of the whole app
 11  verify        run the suite; on failure, one repair request per iteration
```

Stages 1-9 are deterministic and need no model: the same specs produce the same
bytes. Stage 10 is the only place a model is asked for anything, and stage 11 is
the loop that checks it. With no API key configured the run stops after stage 9,
runs the suite once, and reports what fails.

The order is a list in one function: `internal/core/run/pipeline.go`.

## Who owns which generated file

| Path | Written by | May the model rewrite it? |
|---|---|---|
| `pubspec.yaml`, `lib/main.dart`, `lib/app.dart` | project generator | no |
| `lib/stores/*_state.dart` | data generator | no |
| `lib/stores/*_cubit.dart` | data generator (signatures) | **yes** — bodies are business logic |
| `lib/pages/*.dart`, `lib/widgets/*.dart` | ui generator | no |
| `lib/wrappers/*_wrapper.dart` | wrapper generator | **yes** |
| `test/*_test.dart` | test generator | **never** — a model that rewrites a test has verified nothing |

The model is handed exactly the files in the "yes" rows and nothing outside that
set is written, whatever the reply contains. The set is built in
`behavior/codegen/flutter/implement.go` (`editableFiles`).

Every generated file opens with `GENERATED BY METACODE`. Pruning uses that
marker to tell the engine's own output from a hand-written file in the same
directory.

## The two axes

The tree is open in two directions, and the folders say which:

- **spec kind** — ui, data, project, behaviors, and later models and groups
- **target language** — Flutter today

So a spec kind has `rules/` for interpreting itself and `codegen/<language>/`
for generating from itself.

```
engine/
├── cmd/metacode/            assembles the target, then runs the pipeline
└── internal/
    ├── core/                what every spec and language has in common
    │   ├── model/           the domain objects. No imports: the leaf of the tree
    │   ├── spec/            find the metacode/ folder, read the YAML, read .env
    │   ├── build/           raw specs -> model, by calling each spec kind's rules
    │   ├── plan/            model -> the work: which wrappers, which tests
    │   └── run/             the stage list, the CLI, the test runner, the fix loop
    ├── specs/
    │   ├── project/{rules,codegen/flutter}
    │   ├── data/{rules,codegen/flutter}
    │   └── ui/{rules,catalog,codegen/flutter}
    ├── behavior/            the centerpiece spec, at its own top level
    │   ├── rules/           scenarios, assertions, widget-event -> store-action
    │   └── codegen/flutter/ the tests, the wrappers, the implement stage
    ├── codegen/
    │   ├── dart/            the Dart writing toolkit, below every generator
    │   └── flutter/         the Flutter target: the step order
    ├── llm/                 client, config, transcripts
    ├── log/                 logger and stage reporter
    └── order/               sorted map iteration
```

### Dependency direction

```
core/model  <-  specs/*/rules, behavior/rules  <-  core/build
codegen/dart  <-  specs/*/codegen/flutter, behavior/codegen/flutter  <-  codegen/flutter
core/{model,plan,run}  <-  every generator
cmd/metacode  ->  everything
```

Two rules keep it acyclic:

- `core/model` imports nothing. Each spec kind's rules package fills its own
  slice of the model, so those packages import the model; if the building lived
  in the model too, it would have to import them back.
- `core/run` never imports a generator. It reaches the implement stage through
  `run.Target`, which `cmd/metacode` assembles.

## How to add a spec kind

1. `internal/specs/<kind>/rules/` — a `Build` that fills its slice of
   `model.App`, and a `Validate` for its own rules.
2. Add the types it needs to `internal/core/model`.
3. Call it from `internal/core/build/build.go`, and its `Validate` from the
   resolve stage in `internal/core/run/pipeline.go`.
4. `internal/specs/<kind>/codegen/flutter/` — the generator, and a line in
   `internal/codegen/flutter/target.go` to put it in order.
5. Add the file to `spec.Paths` and `spec.Parse` so it is discovered and read.

## How to add a language

1. `internal/codegen/<lang>/` — the writing toolkit: layout paths, class names,
   literals, template rendering, the generated-file marker, shape checks. Model
   it on `codegen/dart`.
2. `internal/specs/*/codegen/<lang>/` and
   `internal/behavior/codegen/<lang>/` — one generator per spec kind.
3. `internal/codegen/<framework>/target.go` — the step order, like
   `codegen/flutter`.
4. Assemble a `run.Target` for it in `cmd/metacode/main.go`. Nothing in `core/`
   changes.

## Guard rails

`make check` runs, and must be green before a commit:

- `go vet` and the full test suite
- `deadcode`: nothing unreachable, kept at zero
- `gocyclo -over 12` on non-test code

Generated output itself is not pinned. The unit tests cover each generator, and
`core/plan`'s determinism test generates the counter app 25 times and compares
the trees to each other, so an unsorted map walk still fails the build. What no
test checks is whether today's output matches yesterday's: to see that, run the
engine on `examples/counter_app` and read the diff.
