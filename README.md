# Metacode

Metacode is a tool to generate any production grade code from a set of specifications written in yaml.

## The problem

LLMs are becoming increasingly capable of writing production grade code autonomously.

However, there is a major conceptual Gap: On one hand, text instructions, human imagination, flexibility. On the other hand, very specific implementation details, language syntax, strictly deterministic machines (compilers) and tools (developer tools).

The industry thinks we are solving it with more capable models, but we are just spending too much energy and money on bridging this huge gap.

## The proposal

Two shared domains: 

- Automated code, driven by a set of YAML specs
- Manual code, generated by humans or by AI.

### The centerpiece Yaml Spec: Tests

Automated tests are the centerpiece of Metacode. The format is very simple:

```yaml
When button is tapped, increment counter:
    given: # any condition
    when: homePage.counterButton.onPressed
    then: counterStore.increment

When counter is incremented, increment the store:
    given: counterStore.value = 2
    when: counterStore.increment
    then: counterStore.value = 3

Show counter value on the home page:
    given: counterStore.value = 5
    when: # always
    then: homePage.counterValue = 5
```

It's the traditional standard of the industry on doing tests. But there are some catches:

- What is `button.onPressed`?
- What is `counterStore`?
- What is `homePage`?

They are symbols, and that is precisely what differs those YAML specs from specs used by LLMs. Those symbols are derived and defined from adjacent YAML specs.

### UI Spec

UI Spec is the spec used to define UI elements. Yes, it's a layouting spec, but with the exception that there is no intrinsic logic.

For this situation, the UI spec would look like:

```yaml
homePage:
    stack:
        - center:
            text:
                counterValue
        - aligned.bottomRight:
            counterButton

counterButton:
    button:
        label: "Add"
```

### Data Spec

Now the data spec. It should specify where data comes from and how it's managed.

```yaml
counterStore:
    value: int
    initialValue: 0
    # ephemeral is only memory (no persistant storage on device or cloud)
    type: ephemeral
```

## How it works

Metacode is generally composed of three stages:

1. Spec Parsing: Parses all Specs, including the test ones, extracts known symbols, check for errors.
2. Graph resolution and planning: builds the internal relations between tests, data and UI specs, resolve symbols that will be eventually classes and functions.
3. Code Generation: From the step 2, generate code either automatically or with the help of AI when needed.

### The non-deterministic generation loop

We rely on non-deterministic generation simply because we know that a fully determinstic code generated from a simpler set of instructions is not only informationally feasible, but maybe impossible. 

Also, we want to be simple enough so we delegate the harder parts that code can solve well (business rules).

But for that, we should have a loop, which is very simple and is just a Test-Driven-Development approach.

1. For each spec, the code is generated using a LLM tool
2. We test that spec
3. If the test does not pass, adjustments are done until the test passes.

### Code generation optimization

On an ever increasing codebase, it's natural that new test scenarios will be added, new screens, new data, etc. 

If we always re-generate the same code, we will be losing time and tokens, and even for fully deterministic parts we will be losing time.

For that we need a strategy to keep the existing generated code while introducing new code.

- After every run, metacode stores a cached/locked set of yaml that reflects the latest changes before a new run.
- When invoked again, it will compare the new changes with the old ones and every change/addition/removal of a test scenario will trigger a new code generation.
- As it's done on every code generation, all tests will be run. If any other tests outside the original changes also fail they are evaluated and fixed until they pass.

In the best case possible, it just changes what was actually changed on the spec. In the worst case, it will change the whole codebase (but maybe that reveals the depth of the change in requirements).

## Running it

For now, the command is very simple, as all options should be in the YAML.

`metacode run`

Any errors in any stage will be reported and the progress of the code generation will also be very beatifully reported by the tool, with the all the details on what is happening.

## Counter app example

A complete working example is available under `examples/counter_app`.

### Prerequisites

- [Go](https://go.dev/) (the engine uses a workspace, see `go.work`)
- [Flutter SDK](https://flutter.dev/) with `flutter` on your `PATH`

### Run

```bash
cd examples/counter_app
go run ../../engine/cmd/metacode run
```

This discovers the Metacode specs, generates the Flutter project under `lib/` and `test/`, runs `flutter test`, and fixes failures automatically when an LLM is configured.

### Verify

```bash
flutter test
```

All generated tests should pass.
