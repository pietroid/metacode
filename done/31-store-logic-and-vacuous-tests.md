# 31 — Store Logic, Stale Output, and Vacuous Tests

## Trigger

A second button was added to `examples/counter_app`: `decrementButton`, with
three scenarios including "not decrements when is 0". The run failed, and the
generated `DecrementButtonWrapper` contained this:

```dart
onPressed: value > 0
    ? () {
        final cubit = context.read<CounterCubit>();
        // ignore: invalid_use_of_protected_member
        cubit.emit(cubit.state.copyWith(value: cubit.state.value - 1));
      }
    : null,
```

A wrapper reaching through `cubit.emit` is an anti-pattern, and the floor-at-zero
rule is business logic sitting in the presentation layer. The model was not being
careless. It had no legitimate route: `CounterCubit` had no `decrement` method.

The deterministic path failed on the same spec, and more plainly:

```
lib/wrappers/decrement_button_wrapper.dart:13:53:
Error: The method 'decrement' isn't defined for the type 'CounterCubit'.
```

So this was never an LLM quality problem. Six defects, found by following that
one symptom.

## 1. A store's API was inferred, not read from the spec

`collectActions` harvested actions only from `when: storeName.action`. Every
decrement scenario said `when: decrementButton.onPressed`, a widget event, so
nothing was collected. Then one line added `increment` to every numeric store,
which is the only reason `increment` existed at all. Nothing in the spec named
it either.

**Fix.** `ir.Binding` resolves widget events to store actions once, during
`Resolve`, so the store generator, the wrapper generator and the test generator
all read the same answer instead of each deriving their own. The action name
comes from the widget (`decrementButton` -> `decrement`, `saveButton` -> `save`),
not from comparing the scenario's numbers. Two scenarios that drive the same
event share one binding, which is what makes a rule like "clamp at zero"
expressible: it is a third scenario on an existing action, not a new one.

## 2. Cubit bodies were hardcoded in the generator

`buildMethods` emitted real Dart for exactly `increment` and `decrement` and
`throw UnimplementedError` for everything else. The counter app, compiled into
the engine.

**Fix.** The generator scaffolds the class, the state, and the method
signatures. Bodies are business logic and come from the scenarios through the
fix loop. Each method carries the scenarios that specify it as a doc comment, so
the fix loop and a human reader see the same requirement in the same place.

This is why the fix loop had to be allowed to edit store files, which it was
not: `fixFailure` only ever regenerated wrappers, so the one file it could touch
for a missing store method was the wrong one. It now offers stores first, then
wrappers, so a wiring fix is judged against logic that has already had its
chance to be right.

**Consequence, deliberate.** Without an LLM, store bodies stay unimplemented and
behavior tests fail. `metacode run` says so in those words rather than reporting
a bare failure count.

## 3. Generated tests found buttons by type

`findTapTarget` returned `find.byType(ElevatedButton)` from the widget kind and
ignored its name. With two buttons, every tap test died on "ambiguously found
multiple matching widgets". The dumb widgets already carried
`Key('decrementButton')`.

**Fix.** `find.byKey(const Key('decrementButton'))`.

## 4. The wrapper prompt saw one scenario out of seven

`plan.Tasks[0].ScenarioID`. The page had exactly one wrapper task, from "Show
counter value on the home page", so the model never saw a button behavior at
all. It wired `incrementButtonOnPressed` by guessing from the constructor
signature and missed `decrementButtonOnPressed`, leaving that button dead in the
composed tree.

**Fix.** The prompt carries every scenario the widget's subtree covers, plus the
resolved bindings, so the model is told which Cubit method each event runs
instead of inferring it.

## 5. Stale output was never deleted

Nothing in the engine called `os.Remove`. Renaming `counterButton` and
ungrouping `behaviors.yaml` left the old widget, its wrapper, and four test files
on disk. Those tests still ran and still failed, so one rename produced failures
for scenarios that no longer existed.

**Fix.** `codegen.Prune` removes generated files the run did not produce, from
the directories generation owns. It deletes only files carrying the
`GENERATED BY METACODE` marker, so a hand-written file in the same directory
survives. LLM-written wrappers now get that marker too, since a file nothing can
identify is a file nothing can clean up.

## 6. The fix loop had been disabled for months, silently

The worst of the six, and only visible once the others were fixed.

`parseFailures` extracted the test path with `(\S+_test\.dart)`. `\S+` stops at
whitespace, and every generated test filename contained spaces, so
`increments from 1_test.dart` was truncated to `1_test.dart`. Every failure then
failed to map back to a scenario, the loop logged "could not map failure to
scenario", repaired nothing, and reported itself exhausted. Any run in which the
first test pass succeeded hid this completely.

**Fix.** Two of them. The regex matches the path greedily up to `_test.dart:`,
and failure paths are made project-relative in one place rather than joined onto
the project directory twice. And `pathToID` now slugifies, so generated names
carry no spaces at all.

## 7. The fix loop validated nothing

Found while verifying the above. A fix for a wrapper came back as two bare Cubit
methods, no class, and was written to the wrapper file unchallenged. It went
unnoticed because per-widget wrappers are dead code on the LLM path, so Dart
never compiled the file.

**Fix.** `modules/codegen/dart` now holds the checks both callers need, and the
fix loop discards output that is not a plausible Dart file instead of writing
it. This also removed a duplicated code-fence regex that existed in both the
wrapper generator and the fix loop.

## Result

`metacode run` on the two-button counter app passes on the LLM path, in two fix
iterations, across repeated runs. No wrapper calls `emit`. The floor-at-zero
rule lives in `CounterCubit.decrement`.

## Also closed here

Milestone 29's items 3, 4 and 6, plus its two "related: the fix loop" notes.
Two more of its silent-failure cases went with them: an event with no known
tester idiom used to return an empty action, producing a test that pumped and
asserted without interacting, and `renderAssertion` fell back to asserting on a
store value the scenario never mentioned. Both are errors now.
