# 22 — Modules & Template-Based Code Generation Refactor

## Goal

Reorganize the engine so that spec interpretation and code generation live in per-concern modules (`ui`, `data`, `project`), with the UI catalog inside the UI module, and replace hard-coded Dart strings with embedded template files (Mason-style) for maintainability.

## Scope

1. **Per-concern modules under `engine/internal/modules/`**
   - `ui/` – UI spec rules, the common UI catalog, and UI code generation.
   - `data/` – Data spec rules and store/model code generation.
   - `project/` – Project spec rules and project-scaffold code generation.
   - `shared/` – Small cross-module helpers (casing, Dart literals, string utilities).
   - `flutter/` – Language-level orchestrator that wires the three concern modules for Flutter.

2. **Module contents**
   Each of `ui`, `data`, and `project` contains:
   - `rules.go` – spec-specific validation and interpretation helpers.
   - `catalog/` (UI only) – the catalog of known widgets; moved from `engine/internal/catalog/`.
   - `code_generation/flutter/` – Flutter-specific generator and templates.

3. **Template-based generation**
   - Store original-format files (`.dart.tmpl`, `.yaml.tmpl`) next to the generator code.
   - Use `//go:embed` + Go `text/template` to render them.
   - Templates use `{{.FieldName}}` placeholders; generators prepare a plain data struct and execute the template.
   - No more multi-line raw string literals for generated source files.

4. **Behavior stays in core**
   - `engine/internal/core/ir/behavior*.go` and behavior parsing remain part of the engine core.

5. **Update consumers**
   - `engine/internal/core/ir/builder.go` and `resolver.go` import the catalog from its new location (`modules/ui/catalog`).
   - `engine/internal/cli/run.go` calls the Flutter orchestrator instead of individual generators.
   - All tests move/rewrite to the new packages and continue to pass.

## Acceptance criteria

1. Directory layout matches the module structure described in Scope.
2. `engine/internal/catalog/` no longer exists; catalog lives in `engine/internal/modules/ui/catalog/`.
3. Each Flutter generator uses embedded template files and `text/template`.
4. `go test ./...` passes in `engine/`.
5. `metacode run` in `examples/counter_app` regenerates the same project structure.
6. `flutter analyze` in `examples/counter_app` reports no issues.
7. The old `engine/internal/modules/flutter/{project,store,ui,naming}.go` files are removed; only a small orchestrator remains there.

## Layering notes

- The core remains spec-agnostic where possible; modules own concrete interpretation and generation.
- Templates are plain text files, making it easy for non-Go contributors to tweak generated output.
- `embed` keeps templates bundled into the binary while keeping them editable as files.
- This refactor enables future languages: add `code_generation/swift/`, `code_generation/react/`, etc., without touching core logic.
