# Working on the Metacode engine

This is the internal document: what the engine is made of, what it guarantees,
and the rules that cost something to learn. If you want to *use* Metacode,
read [docs/language/](docs/language/) instead.

Run `make check` before every commit. It gates `gofmt`, `go vet`, the full test
suite, zero unreachable code, and a cyclomatic cap of 12 per non-test function.

## The pipeline

`metacode run` is thirteen stages. The order is a list in one function,
`engine/internal/core/run/pipeline.go`, deliberately readable top to bottom.

```
 1  discover      find the metacode/ folder above the working directory
 2  parse         read project.yaml, data.yaml, ui.yaml, behaviors.yaml, models.yaml
 3  build         raw YAML -> model, by asking each spec kind's rules
 4  resolve       cross-reference symbols, resolve widget-event -> store-action
 5  scaffold      write the project, the models, the stores, the dumb widgets
 6  plan          which widgets need wrappers, which scenarios need tests
 7  wrappers      write the layer that wires widgets to stores
 8  tests         write one test per scenario
 9  prune         delete generated files whose spec source is gone
10  diff          compare the specs against metacode/.lock, freeze what is unchanged
11  implement     one LLM request writes the behavior of what is not frozen
12  verify        run the suite; on failure, one repair request per iteration
13  lock          record the specs this run understood
```

Stages 1-9 are deterministic: same specs, same bytes, no model. Stage 11 is the
only place a model is asked for anything. With no API key configured the run
stops after stage 10, runs the suite once, and reports what fails.

Stages 1-9 run in full on every run, whatever the diff says. They cost
milliseconds and no tokens, and skipping some of them would buy nothing while
opening a class of bug where stale output survives a rename. So the diff gates
stage 11 and nothing else, which also makes it safe: the worst a wrong diff can
do is ask a model for more or less work than needed, never leave the tree
inconsistent with the specs.

## Who owns which generated file

| Path | Written by | May a model rewrite it? |
|---|---|---|
| `pubspec.yaml`, `lib/main.dart`, `lib/app.dart` | project generator | no |
| `lib/models/*.dart` | model generator | no |
| `lib/stores/*_state.dart` | data generator | no |
| `lib/stores/*_cubit.dart` | data generator (signatures) | **yes** — bodies are business logic |
| `lib/pages/*.dart`, `lib/widgets/*.dart` | ui generator | no |
| `lib/wrappers/*_wrapper.dart` | wrapper generator | **yes** |
| `test/*_test.dart` | test generator | **never** |

The "yes" rows are the whole allowlist, built by `ownedFiles` in
`behavior/codegen/flutter/implement.go`. `editableFiles` narrows it to what one
run asks for; the allowlist is the wider set, and pinning the narrow one would
let it widen unnoticed on any run whose diff happened to be small. Anything else a reply contains is
logged and dropped, and the paths written come from the allowlist rather than
from the reply. Two tests pin this: one behavioral
(`TestApplyIgnoresFilesItDoesNotOwn`), one structural
(`TestEditableFilesOwnsOnlyStoresAndWrappers`). Do not widen it casually. A
model that can edit the suite has verified nothing.

Every generated file opens with `GENERATED BY METACODE`. Pruning uses that
marker to tell the engine's output from a hand-written file in the same
directory.

A file in the **yes** rows carries one of two headers, and the difference is
load-bearing. `- SCAFFOLDING ONLY` means a generator wrote it and no model has,
so the next run may overwrite it. `- DO NOT EDIT BY HAND` means a model has
written it, so no scaffold step touches it again. `dart.IsStub` and
`dart.IsImplemented` ask those two questions, and the stub form is a suffix of
the same line so pruning still matches both with one string.

## The two axes

The tree is open in two directions, and a folder is one or the other:

- **spec kind** — ui, data, project, models, behaviors
- **target language** — Flutter today

A spec kind has `rules/` for interpreting itself and `codegen/<language>/` for
generating from itself. A new directory level needs a reason on one of those
axes.

```
engine/
├── cmd/metacode/            assembles the target, then runs the pipeline
└── internal/
    ├── core/                what every spec and language has in common
    │   ├── model/           the domain objects. No imports: the leaf of the tree
    │   ├── spec/            find the metacode/ folder, read the YAML, read .env
    │   ├── build/           raw specs -> model, by calling each spec kind's rules
    │   ├── plan/            model -> the work: which wrappers, which tests
    │   ├── lock/            the specs the last run understood, and what changed
    │   └── run/             the stage list, the CLI, the test runner, the fix loop
    ├── specs/
    │   ├── project/{rules,codegen/flutter}
    │   ├── model/{rules,codegen/flutter}
    │   ├── data/{rules,codegen/flutter}
    │   └── ui/{rules,catalog,codegen/flutter}
    ├── behavior/            the centerpiece spec, at its own top level
    │   ├── rules/           scenarios, assertions, widget-event -> store-action
    │   └── codegen/flutter/ the tests, the wrappers, the implement stage
    ├── codegen/
    │   ├── dart/            the Dart writing toolkit, below every generator
    │   └── flutter/         the Flutter target: the step order, and pruning
    ├── llm/                 client, config, transcripts
    ├── log/                 logger, stage reporter, spinner
    └── order/               sorted map iteration
```

### Dependency direction

```
core/model  <-  specs/*/rules, behavior/rules  <-  core/build  <-  core/lock
codegen/dart  <-  specs/*/codegen/flutter, behavior/codegen/flutter
core/{model,plan,run}  <-  every generator
cmd/metacode  ->  everything
```

Two rules keep it acyclic. `core/model` imports nothing: each spec kind's rules
package fills its own slice of the model, so those packages import the model,
and if the building lived in the model it would have to import them back.
`core/run` never imports a generator: it reaches the implement stage through
`run.Target`, which `cmd/metacode` assembles.

## Standing rules

These are the ones that were learned the hard way. Everything else that is
worth knowing is a comment next to the code it governs.

**One scenario, one test, against the whole app.** A scenario is never split by
layer. An earlier version compiled a multi-layer scenario down to a store unit
test, which passed while the button that was supposed to call the store was
wired to nothing.

**Ask once, with everything.** One request implements the whole app; one
request per fix iteration carries every failure. Generating a wrapper at a time
and repairing a test at a time meant every request saw one slice of the
problem, which is how a Cubit came back with placeholder bodies: the request
that wrote it had never been shown the tests those methods had to satisfy.

**One prefix per run.** Every call of a run opens with the same bytes: the
rules, the spec, the tests, the generated code the model reads. That block is
sent with a cache breakpoint, so the repairs re-read it at a tenth of the
price instead of paying for it again. Everything that differs between the
implement call and a repair — the editable files as they stand, the failures,
the instruction — goes after it. The two requests used to open with different
sentences, which put the difference at byte zero and made the breakpoint a
surcharge rather than a saving; `TestRepairReusesTheImplementPrefix` pins it.

**The spec and its tests are printed once, together.** A scenario and the test
it compiles to are one thing said twice, so the prompt shows the scenario and
then only what its test adds: the four holes it fills in a skeleton printed
once. What it adds is not derivable by reading the scenario — two `then` lines
that look alike compile to different idioms, one searching rendered text and
the other reading a property off a widget — so the Dart stays even though the
prose around it goes.

**The action a widget event runs comes from the spec.** From the alias the
author wrote on the prop, minus a leading `on`; from the widget's name minus
its kind suffix only when there is no alias. Never from the values a scenario
uses — an earlier rule compared given to then as integers and answered
"increment" when then was larger, which named every button on a string store
`increment` and could not describe "clamp at zero".

**A store action body is business logic, so no generator writes it.** The
signature comes from the spec; the body comes from the scenarios through the
implement stage. The signature has to be the one the model would have written,
or it is not a contract: a row's action takes `int index`, because the wrapper
of a row already knows which row it is.

**A wrapper composes the dumb widget; it does not re-render it.** One
constructor call. A widget that needs wiring is reached through its own
wrapper, so the shape of the tree stays in the generated widgets and each
wrapper wires its own widget and nothing below it.

**The scaffold does not guess at values.** Which store field a variable
displays is behavior; the implement stage writes the BlocSelector. The scaffold
used to infer it by matching a scenario's given against its then, which
answered only for a store holding one scalar and was overwritten everywhere
else.

**The lock holds specs, the diff runs on the model.** `metacode/.lock/` copies
the five spec files and nothing derived from them: storing the resolved
`model.App` would pin the serialized shape of a type that changes whenever a
spec kind does. But the comparison is not on that text. The locked specs are
rebuilt in memory and two `model.App` values are compared, so a comment edit
and a reordered key are not changes, and the freeze set can follow a scenario
to the wrapper it reaches, which is resolved at stage 4 and invisible in YAML.
A lock that no longer builds under the current engine is not an error: it means
a full regeneration.

**Two signals decide what a model may rewrite, and neither can replace the
other.** The lock says what the author changed. The file's own header says
whether it has ever been implemented, which is the only thing that survives a
deleted `lib/` or a fresh clone, and a spec diff structurally cannot see those.
Signature drift is the third and smallest: a preserved Cubit missing an action
the specs added is unfrozen and told which one it owes.

**The lock is written whenever a run reached the suite, red or green.** It
records the last input the engine *understood*, not the last run that worked. A
parse, build, or resolve failure leaves the old lock alone, because the next
run would otherwise diff against a state that never existed. A failing suite
writes, because the result of a run is observed on the next one rather than
remembered: an empty diff still runs the suite, and a red suite still enters the
repair loop with everything unfrozen. There is no green flag in `engine.json`
for that reason.

**A repair sees every owned file, whatever the diff said.** A run reaches a
repair because something the diff called untouched is broken, which is exactly
the case the classification is allowed to get wrong. That is also why freezing
lives in the suffix and not in the prefix: the prefix is byte-identical across
a run, and a file listed there as "never change" could not become writable in
a repair.

**Where a generated file goes is decided once**, in `codegen/dart/layout.go`.
Nothing else in the tree restates it, so a renamed file cannot be both written
and pruned. Scenario names are prose, so file names are slugs, and two
scenarios that slug to one name are an error rather than a silent overwrite.

**A test with no interaction is not a test.** A `then` that cannot be turned
into an assertion, or an event with no test idiom, is an error. Falling back to
something vacuous reports a scenario as covered when nothing checks it.

**Find widgets by key, not by type.** The one exception is `.count`, which is
the single question a key cannot answer.

**Map iteration is sorted everywhere it can reach output.** Use
`internal/order`. `core/plan`'s determinism test generates the counter app 25
times and compares SHA trees, so an unsorted walk fails the build.

**Comments carry the rule, not the history.** State what is true now and why,
not what it used to be, unless the old behavior is the reason the rule exists.

## Adding a spec kind

1. `internal/specs/<kind>/rules/` — a `Build` filling its slice of `model.App`,
   and a `Validate` for its own rules.
2. Add the types it needs to `internal/core/model`.
3. Call it from `internal/core/build/build.go`, and its `Validate` from the
   resolve stage in `internal/core/run/pipeline.go`.
4. `internal/specs/<kind>/codegen/flutter/` — the generator, plus a line in
   `internal/codegen/flutter/target.go` to put it in order.
5. Add the file to `spec.Paths` and `spec.Parse` so it is discovered and read.
6. Document it in `docs/language/`.

## Adding a language

1. `internal/codegen/<lang>/` — the writing toolkit: layout paths, class names,
   literals, template rendering, the generated-file marker, shape checks. Model
   it on `codegen/dart`.
2. `internal/specs/*/codegen/<lang>/` and `internal/behavior/codegen/<lang>/` —
   one generator per spec kind.
3. `internal/codegen/<framework>/target.go` — the step order, like
   `codegen/flutter`.
4. Assemble a `run.Target` for it in `cmd/metacode/main.go`. Nothing in `core/`
   changes.

## Flutter target specifics

- State management is `flutter_bloc`. One Cubit per store, an immutable
  `Equatable` state class with `copyWith`, and a `.seeded` constructor so a
  generated test can set up a scenario's given without reaching into the store.
- A UI symbol becomes a `StatelessWidget` named in PascalCase, taking a
  constructor parameter per variable, per event, and per wired child. It holds
  no logic.
- Files are `snake_case`, classes `PascalCase`, members `lowerCamelCase`.
- Styling props are not generated. That is a spec kind that does not exist yet.

## The lock

`metacode/.lock/` is committed alongside the specs, so a teammate's first run
after a pull is incremental too and the diff is reviewable in a pull request.
The cost is a conflict on the lock whenever two branches touch the specs;
resolving it is trivial, because deleting the lock only means one full run.

`engine.json` holds a hash of `PromptRules`, and only that. Every deterministic
stage reruns in full, so a generator change needs no invalidation; what
invalidates a preserved implementation is a change to the instructions the
model was working under.

`metacode run -regenerate` ignores the lock for one run. Deleting the directory
does the same thing. Reach for the flag when you suspect the diff is lying.

## Checking generated output

The output tree is not pinned by a golden test. Unit tests cover each
generator, and the determinism test proves a run is reproducible, but nothing
checks today's output against yesterday's. To see what a change does, run the
engine on `examples/counter_app` or `examples/focus_app` and read the diff.

## Not built yet

**Multiple stores.** One store per project, enforced at the resolve stage.

**Grouping support beyond scenarios.** Groups nest in `behaviors.yaml` and
become part of a scenario's identity, but nothing else reads the group path.
